# Core Native 整批测试稳定性修复

## 背景
专注整批回归曾在旧同步用例中 SIGSEGV（SQLiter Lock.unlock / ObjC 引用转换），复跑又停在 JSON 序列化 / Native GC。单例通过不能作为整体稳定性验收。

## 目标
- 用整批测试复现，确定崩溃与 GC 卡顿的原因与影响边界。
- 修复真正的生命周期、内存或运行时缺陷，保留原测试断言与测试覆盖。
- 修后执行未过滤的 Core Native 完整回归并重复运行，记录测试数量、失败、耗时和默认 GC 配置。

## 非目标
不修改 Android 新看板、概览统计、全量历史及三端 UI；不以跳过测试、拆进程、禁用 GC 或吞异常冒充修复；不顺手重构同步协议。

## 用户场景
连续执行数据库、专注、同步与通用领域测试时，原生内存可正常回收，测试进程不会崩溃或无限等待 GC。

## 验收标准
- 记录修前复现/采样和能区分假设的证据。
- 新增针对根因的回归覆盖，保留旧同步和专注用例。
- 默认 GC 下无过滤的 macosArm64Test 连续至少三轮通过，零失败/非预期跳过，检查资源释放。
- 若修复涉及共享代码，Android Core 单测和适用编译验证；如涉及生产平台构建配置，明确产物影响与交付状态。

## 风险与约束
现有多任务脏工作区不回滚、不整体提交；仅增量修复稳定性相关文件。依赖/运行时调整须先查本地源码及上游原始依据。大型批次后编译；修改核心文件不超过1000有效行。没有 schema/公共接口破坏计划，若需要 breaking change 先另行保护。
